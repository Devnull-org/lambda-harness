Start with what you need

Conversations keep each response between your replies, including interview questions and specification drafts. Older interview responses are restored from saved task journals when available, without rerunning the model.

The sidebar names the active project and shows its checkout path. Click the project name to collapse or expand navigation and saved work. Memory and Settings pages show the same identity and have project-specific URLs. Use Workspace, a saved task, or your browser's Back button to return to a conversation. Switching pages preserves unsent messages and memory drafts in this tab; refreshing or closing the tab discards unsaved text.

Memory, conversations, backend preferences, and agent selections belong to this project. The Agents catalog and provider logins can be reused across projects. Open Projects to add an existing Git checkout or remove an entry. Use the sidebar's project picker to switch. Each tab stays attached to its own project.

Removing a project leaves its source, conversations, memory, settings, and worktrees on disk. Re-add the same checkout to return to them. Stop running work before removing its project. Switching projects opens a fresh page; the browser warns if you have unsent text.

Settings saves the preferred backend for future sessions. Choose backends and models on the website. Automatic discovery picks a backend for the session without changing the saved preference.

Choose General chat for an ongoing conversation: ask questions, discuss code, or brainstorm. Project context is available when relevant. There is no interview, approval, or finish step. Send a message and return to the saved chat whenever you like. Chat does not change code; use a separate task when you want to implement something.

Every task conversation has a Model for the next response picker above the message box, including explorations, interviews, reviews, and the agent workshop. You can also choose a model when starting a new task. The picker detects the backend and lists models from its installed provider tool. Choose a model for the next reply, or keep the configured default. Use Refresh models after changing provider accounts. General chat replies show the model used when the provider reports it. Loading the list does not send a prompt or interrupt your conversation.

After you send a question, a Thinking… indicator stays in the conversation until the response arrives. It also shows when a request is sending or stopping, or when the connection is lost.

Choose Explore to understand code, compare approaches, and ask follow-up questions. You can stop after the discussion without writing code.

Choose Plan a feature or fix to work through requirements. The interviewer asks questions until you have a specification you can approve.

Give the task a name, choose a base branch or commit, and describe your idea. Names can include spaces, such as Review documentation. Use up to 64 letters, numbers, spaces, underscores, or hyphens, starting with a letter or number and with no spaces at either end. Each task gets its own worktree from the chosen commit. Uncommitted changes in your original checkout stay there.

Use an existing local branch or an already fetched remote branch. GitHub PR URLs in the review option are fetched for you.

Open a saved task to find its Task worktree panel above the conversation. Use Copy path to open the folder in your editor or terminal on the computer running the harness. The path stays available when a task is paused or finished.

Review a PR or branch

Choose this option to inspect an existing change with the selected code reviewer, security reviewer, documentation reviewer, or all three. Code + security is also available. Enter a branch, commit, or GitHub PR URL. Add an optional focus. No interview or implementation is required.

Documentation review checks guides, examples, API docs, and comments against the implementation, including missing instructions and unclear explanations. Examples are inspected without execution. Choose a specialist under Documentation reviewer on the Agents page. These choices apply to standalone reviews; the feature workflow keeps its code and security review steps.

For local refs, choose the comparison base. The review uses the diff from the common ancestor to the selected head. For a GitHub PR, leave the base empty to use its target branch, or enter a branch or commit to override the comparison. This does not change the PR. The PR must belong to a remote configured in this project. The Nix launcher includes the GitHub CLI; sign in with gh auth login if needed.

Ask follow-up questions or revise the focus, then choose Finish review. Findings stay in the conversation and in review.md in the report directory. No code is changed, no builds run, and finishing does not publish comments. Revisions are pinned; start a new task to review newer commits.

Large reviews use a compact preview plus a complete index of local patch files in the task's reports. Reviewers read those patches as needed and must state any files or visual details they could not inspect. Large diagrams are not silently dropped from the review.

Choose Post comment on GitHub on a finding to publish just that finding through your existing gh login. The harness checks the PR revision and diff location, avoids duplicate comments on retry, and records the returned link. It does not approve the PR or request changes.

Choose Check documentation links to check links in changed Markdown and HTML files using lychee, included with Nix. Without Nix, install lychee separately. Results appear in the task and documentation-links.json. Broken links are separated from access restrictions, network failures, and site routes needing a rendered-site check. The checker does not run repository scripts or build the documentation.

Write tests

Choose a base, name the Cabal packages, describe the scope, and list behaviors to test, one per line. Select a Failing regression test (TDD) or Passing coverage for existing behavior.

The agent writes tests, fixtures, and necessary Cabal test wiring. The harness runs lint, strict compilation, Nix checks, and Cabal tests. Inspect the diff, ask questions, or request revisions. Approve tests commits the validated tests and finishes the task. Implementation never starts from this option. Use your normal Git process to take the commit from its worktree.

You choose each next step

  1. Interview. Answer questions, challenge assumptions, and approve the specification when it is ready.
  2. Write failing tests. Inspect the tests, ask questions, and approve them before implementation. For changes covered by existing tests, choose Implement using existing tests or Refactor using existing tests instead. The existing suite, lint, compilation, and Nix checks must pass before coding and after every patch.
  3. Implement. A Haskell specialist writes focused patches against the approved tests.
  4. Refactor. Simplify the code and comments while keeping tests passing.
  5. Review. Haskell and security reviewers examine correctness, performance, trust boundaries, and recovery. Resolve their findings.
  6. Code walkthrough. Optionally answer questions about the finished code. You can require this when creating the task.
  7. Local handoff. Prepare reports and a PR description. Publish through your normal process when you are ready.

Finishing a phase does not start the next one. A completed exploration can lead to an interview later; it does not approve coding.

A coding agent can ask for permission before applying a patch. Changes to tests, protected Cabal settings, or build configuration request it automatically. A permission card in the conversation shows the reason, affected files, and proposed diff. Approve changes and continue applies that exact patch and runs validation. Deny and revise sends it back without applying it; Request changes lets you provide revised instructions. Ask a question can answer a question or revise the pending patch when you request an edit, such as adding code comments. Review the updated diff before approving it. Approval covers one patch, not future changes.

A short bell announces each new patch permission request or validation stop that needs your attention. Use Permission sound in the sidebar to mute it. Your browser remembers this choice. Interact with the page once to enable audio; keep the page open while the agent works.

During implementation, the conversation reports applied patches and validation results. If automatic repairs pause, use Ask a question to ask what failed or request the next fix. A repair request continues from the current worktree and runs validation again. Protected changes still request approval. You do not need to restart the task or choose a different message action.

After the interview you can also choose Explore for an assessment or Requirements interview to revise the scope. If no test patch is appropriate, the test author explains why and waits for your decision. Choose another step returns to these options, including after an older failed test-generation attempt with a clean worktree. It does not discard files or start coding.

Stay in control of the conversation

Codex can request additional runtime access in the task conversation. Review the reason, command or network destination, and requested access, then choose Approve request or Deny request. The same model turn continues with your decision. The permission bell announces new requests; Stop model cancels a pending one. Runtime permissions are separate from patch approvals, and no permanent access rule is saved. This requires a provider with native approval support.

Enter adds a line. Send or Ctrl/Command+Enter submits your message. Only an approval button approves work.

Stop model, beside Send below the chat, interrupts generation. Open Activity log below the message box for detailed progress. Use Edit previous message to change direction, or Retry unchanged to repeat it. Submitted messages remain in history.

During validation, use Stop checks to pause and keep partial logs. Your changes are saved, and no automatic repair starts. Use Recheck when you are ready to run validation again.

Resume returns to a saved phase. Start a fresh attempt creates another task while keeping the original.

Use the × beside a task in Saved work, or Delete task at the bottom of its conversation, to remove it, including completed reviews. Type its name to confirm. Deletion permanently removes its history, reports, local branch, and worktree, including uncommitted work. Export a handoff first if you want a copy. Your source checkout, project memory, other tasks, and published GitHub comments are kept. Stop running work before deleting a task.

Pick up from your phone

Connect Tailscale on both devices using the same account, then launch the harness with --tailscale: 

nix run --refresh github:Devnull-org/lambda-harness -- \
  --state-dir ~/.local/state/lambda-harness --tailscale

Open the printed Phone HTTPS address in your phone's browser. It is also under Open on your phone in the sidebar. Add it to your home screen for quick access. Expand the project name to navigate.

Both screens share the same tasks and approvals. The agents run on your computer, so keep it awake with the harness and Tailscale running. Closing your phone's browser leaves work running. Stopping the harness removes its phone connection. Launch without the flag for local-only use.

If Tailscale asks to enable HTTPS, follow its setup link and launch again. If the default HTTPS port is in use, add --tailscale-port 8443. Keep your usual repository and state directory options. Access is restricted to your Tailscale user account.

Your agent catalog

Open Agents to browse avatars, roles, languages, and expertise. View full instructions, search the catalog, or choose Add agent to start a guided conversation. Describe the help you need; the builder suggests practices and explains tradeoffs. Ask for changes, including a different avatar, before saving.

Each agent has a distinct portrait based on its saved ID and avatar style. The portrait stays consistent across projects, clones, and name changes.

Edit starts a conversation about an existing agent. Its definition changes only when you choose Save to repository. Saved agent conversations live on the Agents page, where you can return to unfinished drafts.

Definitions and avatar choices live in agents/*.json in Git. Source launches detect the harness checkout. If you launch an installed package or directly from GitHub, clone your agent repository and select its checkout under Agent repository. The bundled catalog is read-only.

Saving writes a local Git change. Review it, commit it, and push it to share with the team. Teammates pull and refresh the catalog. The website never commits or pushes definitions automatically. Conversations and project selections stay local.

Use Agents for this project to choose a specialist for each role. New tasks keep a fixed copy of their definitions; editing an agent does not change existing tasks. A new agent is not assigned automatically.

Haskell and Nix coding checks are supported today. Other languages can use chat, exploration, and review agents. A Rust coding definition can be saved, but it needs a supported toolchain before it can be assigned to coding stages. Agent instructions cannot bypass approvals or change permissions.

Fresh context for each agent

Agents share the task request, requirements, project memory, code, approved tests, and recorded check results. Each role gets its own conversation, without other agents' discussions, exploration conclusions, or patch summaries. Findings you select for repair are passed to the coding agents.

Follow-up questions keep that agent's own conversation. Reviewers do not receive one another's findings; a new review pass also leaves out earlier review conclusions. Your complete history stays visible here. Older answers without a recorded author stay visible but are left out of prompts when their owner cannot be determined.

This separates prompt context, not filesystem access. Agents still inspect the same task worktree and are instructed not to look up other agents' reports.

Project memory

Open Project memory in the sidebar. Read and edit notes about architecture, invariants, decisions, and terminology, then choose Save memory. Notes are included in full, up to 32,000 UTF-8 bytes. No model call or repository edit is involved.

In General chat, say “Save this to project memory” or ask to remember a specific point. The harness appends the note and shows Saved to project memory with the exact text and a link to its version. That chat uses the new memory immediately; other tasks keep theirs. Failed saves show a reason. Editing or deleting existing notes still uses the editor.

Add repository paths, one per line, to save references. Adding a path reads all listed files from committed HEAD. Editing notes or removing a path keeps the retained source contents. Refresh sources & save reads them again; uncommitted edits are excluded. Expand Saved source contents to read full copies.

What agents receive shows notes and excerpts, with up to 4,000 characters and 100 symbols per matching source. Changed sources are flagged with no excerpt. Preview the selected task to compare against its own worktree and pinned memory. Repository instructions and conversation history are separate.

Version history lets you inspect earlier versions. Make this current restores one for new tasks. Clear both notes and paths and save to empty current memory; history is retained. A conflicting save keeps your draft. Copy edits you want to keep before choosing Discard draft & load current. Unsaved drafts are lost on page reload.

Existing tasks keep their version until you choose Use viewed version for selected task, between completed phases or general chat messages. Pending reviews keep their original memory. Memory is local to this project's harness state directory.

Pick up where a teammate stopped

In Settings → Export handoff, select up to 30 saved tasks and download the file. A task also has its own Export handoff button. Uncheck all tasks to share only project memory. Export leaves your local work intact.

Your teammate opens their clone in Projects, then chooses Settings → Import handoff. Review the preview and choose Import paused work. Each task gets a fresh worktree. Open it, inspect the conversation and files, then choose Continue from saved step. No model runs until you choose a later action that needs one.

Conversations, specifications, test plans, reviews, check evidence, reports, pinned agents, project memory history, task commits, and unfinished edits travel together. The destination checkout must contain the original base commit. Fetch it from your team's repository if the preview reports it missing; later task commits are included in the file.

Existing tasks keep their names; incoming collisions get an -import-N suffix. Existing project memory stays current. Imported versions are available in Memory, and each task keeps its pinned version. A project without memory adopts the incoming current version. Import does not change agent assignments, the shared catalog, provider logins, or validation commands.

Every imported task pauses for your review. Earlier approvals and checks remain historical evidence. Pending test approval requires Recheck on your machine before approval becomes available. Import itself runs no agents, builds, or tests.

Handoffs are limited to 32 MB and saved review gates or completed phases. Stop running work before exporting. If the worktree changed outside its saved gate, recheck or recover that task first. Agent design conversations are excluded; share saved definitions in Git. Ignored files, build outputs, settings, logins, and raw backend diagnostics are excluded. Review the file before sharing: your conversations, notes, and code may contain private information.

This is a snapshot, not live synchronization: agree who continues the work. Prepare local handoff in the coding workflow still prepares reports and a PR description; the export/import controls transfer saved work to another developer.

Bring your existing model login

Automatic selection checks configured backends and makes a small generation request without project data. If several work, choose one on the page. Checks consume a small amount of provider usage.

Use Project settings to select a backend. Check backends and resume repeats discovery for a saved task. Switching providers preserves the task's history and approvals.

Sign in through your provider's normal CLI login flow. Login and usage allowances are separate: a signed-in provider may still refuse a request. Failures pause work with diagnostics; the harness does not silently switch providers.

Custom model routing and hosted API bridges are described in the backend reference.

Tests first. Reviewable patches.

Before writing tests, coding, or running checks, the harness reads the project's test suites, runner entry points, Nix setup, CI, and repository instructions. It saves its findings under Project test setup in the task. Unclear prerequisites or commands become questions before execution. HLint is not assumed.

Project tests run through Cabal. Every code patch runs lint, a strict build with -Werror, Nix checks, and the selected package's tests inside the target's Nix environment.

Identified failing assertions are allowed during the test-first phase. Build errors, runner errors, and unrelated failures block progress. Later phases require passing checks.

Reusing existing tests can use Cabal's normal passing suite summary. TDD and named coverage checks need individual test results. The current detailed-report adapter supports JUnit; discovery checks whether the runner already provides it and asks if support is missing. It never installs a reporter or changes test code during inspection.

A user-owned TOML file can adapt your team's commands:

[validation]
lint = ["just", "lint"]
build = ["just", "build-strict"]
nix = ["just", "check"]
test = ["just", "test", "{package}"]
junit_glob = "test-reports/{package}/**/*.xml"

Pass the file with --config when launching the server. Settings are saved with new tasks. See the validation reference for defaults, red-phase failures, protected tests, and commit signing.

How the local website runs

The browser connects to a small Python server on this machine. That process accesses your checkout, saves conversations, and invokes model backends. If an assistant started it, the server may be running in its background session even though your terminal is idle.

To start it yourself from any directory:

nix run --refresh github:Devnull-org/lambda-harness -- \
  --state-dir ~/.local/state/lambda-harness

--state-dir is required. Choose a persistent directory outside your project checkouts and reuse it every time. It holds your project list, conversations, memory, logs, and worktrees. The path above is an example; if you already have saved work, use its existing directory. Startup prints the resolved path. Storage is never moved or selected automatically.

Open the printed URL and add a checkout from Projects. You can also append --repo "/path/to/project" to open it immediately. Keep this command running. Closing the browser leaves work running. Ctrl+C in the server terminal stops active work; submitted messages and completed steps remain saved.

From a harness clone, use nix run . -- --state-dir ~/.local/state/lambda-harness --repo "/path/to/project". Nix resolves . before reading --repo, so run that form from the harness directory.

Without Nix, install Git, uv, and your chosen backend CLI, then run this from a harness clone: 

uv run --locked --no-dev python -m lambda_harness \
  --state-dir ~/.local/state/lambda-harness --repo "/path/to/project"

Nix is optional for exploration and interviews. Code validation still needs the project's Nix environment.

Common startup options

Option Purpose
--repo PATH Optional initial Git checkout. Omit to start on Projects.
--port PORT Local port, default 8765. Use 0 to choose an available port.
--state-dir PATH Required. Project list, conversations, memory, logs, and worktrees. Keep it outside all registered checkouts and reuse it on every launch.
--config FILE User-owned backend and validation configuration.
--nix-flake PATH Dependency flake override for the initial --repo only. Other projects use their own worktrees.
--help All server startup options.

When upgrading, stop the old server and start the new version. Keep the same checkout and state directory to reopen saved tasks. Do not move registered worktrees.

The server listens only on 127.0.0.1. Model calls use your chosen provider. Backend access is governed by its configuration; the harness is not an operating-system sandbox.
